Method and preservation
The same /tmp binary runs both scenes sequentially, under the common game
lock. Both use hero-mid / sweep /1800 frames /120 warmup /1600x900 / noHUD,
normal16.05 afternoon lighting,3072px shadow map and9tap soft shadows.
Native renderer, frame count, watch-disabled state, actual source counts,
shadow settings and zero GL/cache cleanup errors were checked automatically.

The temporary viewer changes only the watch load guard and its matching
required-load/error condition. All other production objects are linked
unchanged using the actual Makefile compiler flags/libraries/object order.
Production source, objects, rpg and recorded scenery/ground inputs remain
byte-identical: post-run-preservation.json has every check true.

A opens the current project. B is a /tmp project overlay using the exact
saved2640-record castle file and saved village_ground_history.png from
the before/ directory. Its other three scenery sources, models, shaders,
fonts and unchanged ground files link to the current project. The current
compiled atlas and12new mask rectangles remain in both runs. Consequently B
is an almost-old-scene control, not a rollback to the old engine executable.

Source/binary proof: build-manifest.json records production and temporary
viewer/binary SHA256, all exact linked object hashes, compile/link argv and
scenery/ground input hashes. viewer-watch-off.diff gives the sole source
change. world_viewer_watch_off.cpp and diagnostic-runner.py preserve the QA
source/driver. The temporary executable remains at

Interpretation
Disabling watch does not recover smoothness in the current scene. Removing
the added static reinforcements improves this sequential trial, but the
almost-old scene also fails and is well below its historical59.95FPS hero-mid
result. The shared watch update is therefore not the sole cause, and the
current evidence does not establish a watch algorithm defect.

The static additions/residency could contribute: B loads six fewer images,
has lower mean GPU time and lower GTT peak. However, aggregate memory/IO full
stall pressure also drops materially between A and B, while both exhibit
system pressure and neither owned game swaps. One fixed-order pair cannot
separate static-asset GPU pressure from changing external memory/driver
conditions. Preserve both failures; do not replace them with a favorable
rerun or label this integrated acceptance complete. A later same-condition
paired order-reversed control or narrowed per-stage upload timings would
provide stronger causal evidence before any visible quality reduction.

No production fix, quality reduction, extra native run or interactive user
launch was performed. Both native jobs have exited and the GPU is idle.
